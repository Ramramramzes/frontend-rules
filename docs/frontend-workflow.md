# Процесс фронтенд-разработки

## Согласованные решения

- Основной сценарий — доработка существующего проекта.
- На входе обычно Swagger; дополнительно могут быть макет Figma или HTML/CSS от дизайнера.
- Сначала агент изучает задачу и проект, затем предлагает план с критериями готовности.
- Реализация начинается после согласования плана.
- После согласования агент выполняет оговорённый объём самостоятельно, проверяя результат по этапам.
- Существенные изменения объёма или неразрешимую неоднозначность агент выносит на обсуждение. Если контракт API неполон или расходится с фактическим ответом, агент объясняет, чего не хватает и какой сценарий от этого зависит, затем ждёт решения по этому участку.
- Порядок разработки: логика и API → проверка функционала → оформление по дизайну → визуальная проверка.
- Основной подход — FSD, Effector и генерация из OpenAPI. Локальное состояние компонента можно хранить в `useState`.
- Для нового оформления используется Tailwind, если он принят в проекте. Существующий CSS/SCSS сохраняется.
- Компоненты сначала ищутся в текущем проекте. Если подходящего компонента нет, используется основа из shadcn с адаптацией к теме проекта.
- Новые переиспользуемые компоненты сразу разрабатываются адаптивными, с поддержкой светлой и тёмной темы. Недостающий токен можно добавить в тему и указать в отчёте.
- Агент запускает ESLint, сборку и отдельный `typecheck`, если он предусмотрен проектом. Новые автоматические тесты пишет по прямой просьбе.
- Новые строки локализуются там, где есть функционал перевода или он входит в задачу.
- Общая основа — четыре принципа из [rules/karpathy.md](../rules/karpathy.md).
- Инструкции для агента — [rules/frontend.md](../rules/frontend.md).
- Правила UI — [rules/components-and-theme.md](../rules/components-and-theme.md).
- Подключение Figma Design to Code, Playwright CLI и shadcn/ui — [frontend-skills.md](frontend-skills.md).
- Формат карты проекта и инструменты для ориентации в коде — [project-map.md](project-map.md).

## Рабочая последовательность

| Этап | Действия агента | Проверяемый результат |
| --- | --- | --- |
| 1. Изучение задачи и проекта | Прочитать требования и инструкции. Найти аналогичные функции, API-клиент, UI-компоненты и тему по карте проекта или точечным поиском | Известны границы задачи, точки изменения и доступные решения |
| 2. Разбор входных материалов | Изучить нужные методы и схемы OpenAPI. При наличии разобрать Figma или HTML/CSS и выделить элементы и состояния | Определены сценарии и контракты. Пробелы в API вынесены на решение пользователя |
| 3. Планирование | Предложить шаги реализации, проверки функционала и последующего оформления; согласовать план | Есть согласованный объём с критериями готовности |
| 4. Логика и API | Реализовать модель Effector и интеграцию через существующий клиент и типы OpenAPI. Вычислять производные данные из исходного состояния. Собрать интерфейс из компонентов проекта | Сценарий доступен для проверки |
| 5. Проверка функционала | Пройти основной сценарий и относящиеся к нему состояния. Для поиска и фильтрации проверить запоздавшие ответы. Для сохранения проверить повторное нажатие и сохранность ввода при ошибке | Функционал проверен, обнаруженные проблемы устранены или явно описаны |
| 6. Оформление по дизайну | Доработать существующие компоненты до соответствия Figma или HTML/CSS. При отсутствии подходящего компонента адаптировать shadcn под тему | Реализован дизайн с использованием компонентов и токенов проекта |
| 7. Проверка оформления | Сравнить с дизайном. Проверить адаптивность, темы, работу с клавиатуры и фокус. Для изменённого общего компонента дополнительно проверить одно существующее использование, если оно есть | Проверены внешний вид, взаимодействия и переиспользование компонента |
| 8. Сдача | Запустить ESLint, сборку и отдельный `typecheck`, если он есть. Проверить diff, обновить затронутые записи карты и указать результаты, добавленные токены и оставшиеся ограничения | Пользователь понимает, что готово и как это проверено |

Разбор дизайна выполняется до реализации, чтобы учесть структуру и состояния. Основная работа над визуальным соответствием выполняется после проверки функционала.

Если дизайна нет, использовать существующий интерфейс и тему проекта как образец. Отсутствие макета явно отметить; проверять консистентность, адаптивность и темы без утверждения о совпадении с отсутствующим макетом.

Справка для проверок: [производное состояние в React](https://react.dev/learn/you-might-not-need-an-effect), [доступность в Playwright](https://playwright.dev/docs/accessibility-testing), [клавиатура и фокус в модалках](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/#keyboard_interaction).
