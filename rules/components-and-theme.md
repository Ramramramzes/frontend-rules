# Компоненты и тема

Применять при создании и изменении фронтенд-интерфейсов.

## Переиспользование

- Перед созданием компонента найти существующие UI-компоненты, их варианты, публичные экспорты и примеры использования в проекте.
- Использовать подходящий компонент проекта. Если он расходится с дизайном, доработать его до соответствия макету. Если новый вид нужен только в этом сценарии, использовать композицию или добавить вариант, сохранив поведение остальных мест использования.
- Если подходящего компонента нет, взять основу из shadcn и адаптировать её к текущей теме, стилю и расположению UI-кода в проекте.
- Для подбора основы использовать навык shadcn/ui, если он доступен. Сверить `components.json`, алиасы и библиотеку примитивов с реальными импортами проекта. Перед добавлением через CLI посмотреть список затрагиваемых файлов и зависимостей. Перенести нужный компонент в принятую структуру UI, сохранив существующие компоненты и настройки темы.
- Не создавать дубликаты существующих компонентов и не подключать альтернативный UI-kit для уже решённой задачи.
- HTML/CSS от дизайнера и Figma использовать как описание внешнего вида и поведения. Сопоставлять их элементы с компонентами проекта; переносить оформление через существующую тему.

## Тема

- Для нового оформления использовать Tailwind в проектах, где он принят. Сохранять существующий CSS/SCSS в компонентах, которые его используют.
- Перед оформлением изучить механизм темы и принятые токены проекта.
- Брать цвета и остальные доступные значения оформления из темы: фон, текст, границы, состояния, типографику, отступы, скругления и тени.
- Если нужного значения нет, можно добавить семантический токен в тему. В отчёте указать, какой токен добавлен и для чего он нужен.
- Поддерживать светлую и тёмную тему через существующий механизм переключения. Использовать семантические значения, соответствующие назначению элемента.
- При адаптации shadcn заменить несовместимые значения оформления на токены проекта; не вводить параллельную палитру или механизм темы.

## Адаптивность и проверка

- Новый переиспользуемый компонент сразу разрабатывать с адаптивным поведением в рамках поддерживаемых проектом размеров экрана.
- Использовать существующие брейкпоинты и правила компоновки; проверить переполнение и длинный контент, если они относятся к компоненту.
- Проверить светлую и тёмную тему, а также предусмотренные компонентом состояния, например focus, disabled, loading и error.
- Применять переиспользование и тему уже при реализации функционального интерфейса. Точное визуальное соответствие дизайну доводить после проверки функционала.
- После оформления повторно проверить затронутые взаимодействия. Отдельно указать проверки, которые выполнить не удалось.
- При изменении общего компонента проверить целевой сценарий и хотя бы одно существующее место его использования, если оно есть.

## Доступность

- Для изменённых интерактивных элементов проверить навигацию и работу с клавиатуры, видимый фокус и понятные подписи. У кнопки с одной иконкой должно быть доступное имя.
- Для изменённой модалки проверить, что фокус при открытии попадает внутрь, `Esc` закрывает её, а после закрытия фокус возвращается к элементу, который её открыл. Если этот элемент исчез, проверить переход к следующему логичному элементу.
