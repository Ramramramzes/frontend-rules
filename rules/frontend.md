# Правила фронтенд-разработки

Применяй эти правила к задачам на фронтенде. Порядок проверок ниже имеет приоритет над примерами автоматических тестов в общих правилах Карпатого.

## Порядок работы

1. Изучи инструкции проекта и найди нужный код по карте проекта или точечному поиску. Проверь контракт OpenAPI и дизайн, если есть Figma или HTML/CSS от дизайнера. Найди API-клиент, похожие функции, общие компоненты и токены темы. При наличии макета собери его параметры до реализации по разделу «Перенос из Figma и сверка» в правилах компонентов и темы.
2. Предложи план с критериями готовности и согласуй его перед реализацией. После согласования выполняй шаги самостоятельно в оговорённых границах.
3. Реализуй бизнес-логику, интеграцию API и пользовательские сценарии. Проверь функционал и относящиеся к задаче состояния загрузки, ошибок и пустых данных.
4. После проверки функционала доведи оформление до дизайна. До сдачи выполни сверку по разделу «Перенос из Figma и сверка» и проверь затронутые взаимодействия, адаптивность, светлую и тёмную тему. Если Playwright CLI доступен, используй его на этапах проверки поведения и оформления. Пройди изменённый сценарий в браузере и сними скриншоты при проверке дизайна. Если CLI недоступен, используй доступный браузер или укажи, что проверить в браузере не удалось.
5. Запусти ESLint и сборку командами проекта. Если в проекте есть отдельная команда `typecheck`, запусти и её. Если код поменялся после этих проверок, проверь финальную версию. В отчёте укажи результаты и ограничения проверки. Новые автоматические тесты добавляй только по прямой просьбе.

## Навигация по проекту

- Если есть `MAP.md` или другая карта, указанная в инструкциях проекта, открой только относящийся к задаче раздел. Используй путь и ориентир из карты как отправную точку для `rg`. Проверяй сведения по исходному коду.
- Если ориентира нет или он устарел, начни поиск с вероятного слоя FSD, маршрута, API-операции или публичного экспорта. Для поиска исключай зависимости, сборку и сгенерированные файлы, пока задача прямо их не затрагивает.
- При создании карты записывай входные точки, относительные пути и стабильные ориентиры для поиска. Ссылайся на существующую документацию. После изменения пути, маршрута или публичного имени обнови только затронутые записи существующей карты.
- Если в проекте уже есть сгенерированный индекс, обратись к его релевантной части, когда карты не хватает. Для сложных цепочек импортов и вызовов можно использовать уже настроенный локальный Graphify с точечным запросом. Пересборку индекса или графа выполняй по запросу.

## Архитектура и состояние

- Используй FSD и Effector. В существующем проекте следуй принятой структуре и публичным экспортам слайсов. Миграцию чужого стека согласуй отдельно.
- Храни бизнес-состояние в модели Effector и выполняй запросы через эффекты с существующим API-клиентом. Для связей между событиями, сторами и эффектами используй `sample`, для доступа из React — `useUnit`.
- Используй `useState` для состояния, которое нужно только конкретному компоненту, например для показа пароля.
- Храни каждое значение в одном месте. Отфильтрованные списки и другие производные данные вычисляй из исходного состояния, например через `combine` в модели Effector или при рендере компонента.
- При изменении поиска или фильтров проверь порядок ответов. Если старый запрос завершится позже нового, его результат не должен заменить актуальный.
- Для сохранения проверь, что повторное нажатие во время запроса не отправляет дубль. При ошибке сохраняй введённые данные, чтобы пользователь мог исправить их или повторить отправку.

## OpenAPI

- Используй OpenAPI как контракт и запускай генерацию командой проекта. Подключай существующий типизированный клиент. Сгенерированные файлы обновляй через генератор.
- Если для сценария не хватает метода, поля или схемы либо фактический ответ расходится с OpenAPI, сообщи, чего не хватает, что расходится и для чего это нужно. Дождись решения пользователя по затронутой интеграции. Остальные согласованные шаги можно продолжить, если они от этого не зависят.

## Переводы

- Добавляй новые строки в поддерживаемые языки, когда в проекте есть перевод затронутого интерфейса или перевод входит в задачу. В остальных задачах используй текущий язык проекта.
